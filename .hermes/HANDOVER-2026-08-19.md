## Root Causes of "edit nicht möglich" (all now fixed in source)

### Defect 1 — `Keyboard[308]` exception (FIXED, was active in last test)
- A legacy `KeyCode` value (308 = RightShift) was serialized into
  `FPSEditModeController`'s snap-toggle key field. `Keyboard[308]` index is outside
  the valid enum range (1..123) → `ArgumentOutOfRangeException` killed `HandleEditing()`
  every frame.
- **Fix** (compiled in 12:54 build): sanitization in `Start()` + `IsValidKey()` helper.
  Valid keys are 1..123. `Key.MaxKey` does NOT exist in InputSystem `21a28c3a6c83`.

### Defect 2 — No play-mode initialization (FIXED in source, NOT compiled)
- `VolumeProcessor` had **no `Awake()`/`Start()`** (only `#if UNITY_EDITOR OnEnable`).
- All pipeline state — `_pipeline`, `_octreeMesher`, `_octreeMeshFilter`,
  `_meshRenderer`, `_chunkRenderers` — are plain `private` fields that **reset to null
  on play-mode start**.
- Result: in play mode, `EditCell`/`EditBrush` early-return (stale null pipeline) and
  `RebuildOctree` no-ops on `if (_octreeMesher == null) return` → clicks did nothing,
  no exception, no log line. Exactly the reported symptom.
- **Fix:** added `Awake()` that calls `Initialize()` when `Application.isPlaying`
  (guarded by `_initialized` idempotency).

### Defect 3 — Field-name drift dropped the Octree setting (FIXED in source, NOT compiled)
- Scene serializes `dataStructure: 1` (= **Octree**) on the `VolumeModel` GameObject.
- Old C# field was named `dataStructureType` → Unity binds **by field name** → the
  serialized value was silently discarded → processor ran as `VoxelGrid` (flat), so
  the octree edit path was never even reachable.
- **Fix:** renamed field back to `dataStructure` (matches scene), removed the
  conflicting read-only `dataStructure` property, updated all 13 `dataStructure*`
  references. `dataStructureType` no longer appears anywhere.

### Defect 4 (reported separately) — Material not applied on Rebuild
- `surfaceMaterial` was pushed to renderers **only at pipeline init**, never on
  rebuild. So changing the material + pressing "Rebuild Model" re-meshed geometry but
  kept the stale init-time material.
- **Fix:** new `ApplySurfaceMaterial()` (VolumeProcessor.cs L476) pushes
  `surfaceMaterial` to `_chunkRenderers` (flat) AND `_meshRenderer` (octree). Called
  from `RebuildPipeline()` (L490) and the flat `RebuildModel()` path (L847) — i.e.
  **every** rebuild entry point now re-pushes the material.

### `RebuildModel: no objects` warning — NOT a real defect
- Log showed repeated `no objects`, but the scene registry is **correct**: it lists 2
  `VolumeObject`s (fileID `1957898689`, `694204810`), both present in the scene with the
  right GUID `04147a4fd5bca354696815bc69b81de5`. The warning came from the old DLL.
  Expected to self-heal after recompile.

- VolumeProcessor UI keeps the dropdown-based "add object" flow.

- Unity 6000.4.1f1, Windows, Input System active, .NET Standard 2.1 / Mono.
